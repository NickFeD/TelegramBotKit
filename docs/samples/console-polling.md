# ConsolePolling: ручная проверка бота

[Документация](../README.md) · [Webhook](webhook.md)

`TelegramBotKit.Sample.ConsolePolling` использует локальные проекты Core, Polling,
Hosting и генератор. Изменения библиотеки попадают в пример после пересборки;
публиковать NuGet-пакеты для этой проверки не требуется.

## Что проверяют примеры

| Пример | Реализация библиотеки | Назначение |
| --- | --- | --- |
| ConsolePolling | Локальные проекты | Основной стенд ручной проверки polling, команд, middleware и messaging |
| MinimalPolling | Локальные проекты | Минимальная настройка и одна команда `/start` |
| Webhook | Локальные проекты | HTTP-доставка через ASP.NET Core и общее исполнение Hosting |
| PhotoSelector | Опубликованные NuGet-пакеты | Прикладные сценарии выбора медиа; не проверяет текущий локальный Core |

## Подготовка и запуск

Из корня репозитория соберите решение и выполните автоматические проверки:

```powershell
dotnet build TelegramBotKit.slnx -c Release
dotnet test TelegramBotKit.slnx -c Release --no-build
```

Для ручной проверки используйте отдельного тестового бота. Задайте токен через
переменную окружения `TelegramBotKit__Token` или создайте рядом с `appsettings.json`
игнорируемый `appsettings.Local.json`:

```json
{ "TelegramBotKit": { "Token": "YOUR_BOT_TOKEN" } }
```

Локальный файл не включается в Git и publish output. Основной `appsettings.json`
оставьте без токена. Остановите другие процессы, использующие polling
этого же бота. Если раньше был настроен webhook, удалите его перед переключением
на polling, как описано в [руководстве по webhook](../webhooks.md#polling-migration).

Запускайте пример из его каталога: он явно читает `appsettings.json`
относительно каталога запуска.

```powershell
Set-Location samples/TelegramBotKit.Sample.ConsolePolling
dotnet run -c Release
```

Приоритет источников: `appsettings.json`, затем `appsettings.Local.json`, затем
переменные окружения и аргументы командной строки. Последний источник имеет
приоритет. При пустом токене пример сообщает об ошибке конфигурации в консоли
и завершается с кодом 1 до запуска polling.

## Сценарии в Telegram

Начните с личного чата, чтобы проверить базовую обработку независимо от настроек
доступа бота к сообщениям групп.

| Действие | Ожидаемый результат |
| --- | --- |
| Отправить `/start` | Приходит тестовое меню с четырьмя кнопками |
| Отправить `/START` и `/start argument` | Открывается то же меню: проверяются регистр ключа и выделение первого токена |
| Нажать «Callback» | Появляется уведомление «Callback работает», затем сообщение в чат |
| Нажать «Like(123)» | Уведомление содержит `id=123`: аргумент callback передан обработчику |
| Нажать «Trace» | В чат приходит `traceId`, совпадающий с идентификатором в логах middleware; значения `no-trace` быть не должно |
| Отправить `echo`, `ECHO` или `эхо` | Бот отвечает `echo: ...`, сохраняя исходный текст |
| Отправить `echo extra` или неизвестную slash-команду | Срабатывает message fallback с предложением `/start`: текстовые триггеры сопоставляются целиком |
| Отправить `/photo`, затем нажать «Ещё фото» | Приходят фотографии с подписями и inline-клавиатурами |
| Нажать Like под фотографиями | Уведомления содержат `id=42` и `id=99` соответственно |
| Нажать «Wait», дождаться приглашения и отправить `проверка` | Приходит «Получил: проверка»; ответ не должен одновременно попадать в message fallback |
| Нажать «Wait» и не отвечать более 30 секунд | Приходит сообщение о таймауте; после него ожидание можно запустить снова |
| Во время ожидания отправить `/start` | Сообщение принимается как ответ на ожидание, а не как новая команда |
| Изменить своё сообщение, ранее отправленное боту | В консоли появляются сообщения `Routing edited message` и `Message ... was edited`; отдельного ответа в чат этот route не отправляет |

Фотографии загружаются Telegram по внешним URL `picsum.photos`. Их недоступность
нужно отличать от ошибки маршрутизации или регистрации команд.

## Конкурентность и завершение

В конфигурации примера `TelegramBotKit:Polling:MaxDegreeOfParallelism` равен двум.
Повторите сценарий Wait с двумя разными пользователями в разных чатах: каждый
должен получить только свой ответ. Серия `/start` проверяет видимую работу очереди
отправки; в примере включён интервал между запросами в один чат.

Для проверки ответа при занятом единственном слоте установите
`MaxDegreeOfParallelism` в `1`, перезапустите процесс и повторите Wait. Ответ должен
дойти до ожидающего обработчика до таймаута. После завершения проверки верните
настройку, если больше не нужен этот режим.

Остановите процесс через Ctrl+C сначала в простое, затем во время ожидания.
Проверьте завершение хоста и возможность повторного запуска с `/start`.

## Границы ручной проверки

ConsolePolling демонстрирует регистрацию через атрибуты, slash/text/callback,
типизированные callback-ключи, глобальное и route-local middleware, обработку
edited message, message fallback, фотографии, ожидания и queued sender.

Отдельные проверки нужны для webhook, fluent-команд из Routing, reply-клавиатур,
пагинации, редактирования исходящих сообщений, inline-callback без сообщения,
ошибок Telegram и повторных попыток отправки. Callback fallback зарегистрирован,
но отдельной кнопки с неизвестным ключом в меню нет.

Обычные build и run не подтверждают успешную публикацию и запуск Native AOT:
этот режим требует отдельной проверки опубликованного исполняемого файла.
По умолчанию пример собирается без Native AOT, чтобы lock-файл оставался переносимым
между Windows и Linux. Native AOT включается отдельно при публикации.

Гонки регистрации, отмены и остановки, а также ошибки конфигурации нельзя надёжно
проверить несколькими нажатиями: используйте автоматические тесты вместе с этим
списком. Проверка упаковки генератора описана в
[generated commands](../generated-commands.md), нагрузочные измерения — в
[benchmarks](../benchmarks.md). Эта инструкция не является записью о прохождении
живого теста через Telegram.
